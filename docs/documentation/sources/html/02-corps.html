2. Mise en route locale

Parcours le plus court, tel qu'il figure dans le README et dans docs/01-demarrage.md :

git clone https://github.com/Elodias2001/Takienta.git
cd Takienta
pnpm install
pnpm --filter benin-geo build

Pour construire et tester le site :

pnpm build:site
pnpm test:site

pnpm build:site écrit dist-site/. Pour voir le site dans une image locale : docker compose up --build, puis docker compose port takienta-site 8080 donne le port publié (commentaire de docker-compose.yml).

Il n'y a ni compte administrateur, ni jeu de démonstration, ni formulaire de premier accès : le projet n'a ni base ni backend. La création de l'environnement Python local (.venv/) n'est écrite nulle part dans le dépôt Non déterminé à date ; la CI installe les outils avec python -m pip install -r requirements-dev.txt.

7. Ajouter ou corriger une donnée

Il n'y a pas de « collection » à déclarer : les données sont des fichiers produits par le pipeline. La procédure, d'après docs/05-contribuer.md et AGENTS.md :

  1. S'appuyer sur un texte : loi, décret ou publication officielle.
  2. Ajouter le document dans data/sources/ avec son empreinte SHA-256, puis le déclarer dans data/sources.json.
  3. Reconstruire : python3 scripts/construire-donnees.py, puis node scripts/build-data.mjs.
  4. Lancer les tests (§10).
Prudence

Ne jamais régénérer ni éditer les deux instantanés d'identifiants (data/identifiants.snapshot.json, data/identifiants-arrondissements.snapshot.json). Un arrondissement créé plus tard s'ajoute en fin de liste de sa commune ; une suppression laisse un trou. Ne jamais ajouter un accent de mémoire à un libellé : un accent n'est retenu que si un village du même arrondissement l'atteste.

Un alias de commune ne s'ajoute que s'il est relevé dans une source. Les six libellés de la loi qui diffèrent du nom usuel vivent dans data/rapprochement-communes.json.

11. Build et déploiement

11.1 Build

Site : pnpm build:site. Image locale : docker compose up --build. Image de production, pour le serveur (architecture x86_64) depuis un Mac arm64 : docker buildx build --platform linux/amd64 -t ghcr.io/elodias2001/takienta-site:main --load .. Cette dernière commande vient de la pratique de l'autrice, pas d'un fichier du dépôt.

11.2 Déploiement

Le déploiement est manuel : le dépôt n'a aucun workflow de déploiement, volontairement. Les adresses et accès du serveur ne sont pas reproduits ici. Ordre à respecter :

  1. Le DNS du domaine existe avant le démarrage du conteneur, sinon la validation Let's Encrypt de Traefik échoue.
  2. L'image linux/amd64 est transférée sur le serveur (docker save compressé, puis docker load à l'arrivée), sans registre.
  3. Le fichier docker-compose.prod.yml du serveur est celui du dépôt ; il est comparé avant de le remplacer.
  4. Dans le dossier du projet sur le serveur : docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d, avec --force-recreate pour recréer le conteneur à l'identique.
Prudence

Le serveur est partagé avec d'autres projets. Le déploiement ne touche que le dossier et le conteneur de Takienta, jamais Traefik ni un autre projet. Une chaîne de commandes qui enchaîne le build et le transfert avec && peut recharger l'ancienne image si le build échoue au milieu d'un tail : vérifier le code de sortie du build avant le transfert.

11.3 Vérifications après déploiement

  • docker inspect takienta-site --format '{{.HostConfig.Memory}} {{.HostConfig.MemorySwap}}' : 134217728 et 201326592 attendus (128 Mo et 192 Mo).
  • L'état du conteneur est running et son contrôle de santé healthy.
  • Les pages /, /carte, /comparer et /provenance répondent 200 ; curl -sI montre les en-têtes de sécurité.

11.4 Retour arrière

Aucun mécanisme n'est écrit : l'étiquette main désigne la dernière image chargée. La procédure de retour à une image précédente n'est pas définie Non déterminé à date.

11.5 Publier les paquets

La publication est manuelle et se fait avec un compte et un jeton personnels, conservés hors dépôt. Pratique relevée le 09/10/2026 :

# JavaScript, depuis packages/js
npm publish --access public

# Python, depuis packages/python
python -m build
twine upload dist/*

twine n'est pas dans requirements-dev.txt. Après publication, installer le paquet depuis le registre dans un dossier vide et appeler chercher pour vérifier. Quand un registre est publié, passer l'indicateur correspondant de publie à true dans site/config.mjs et écrire la ligne d'installation dans docs/01-demarrage.md : un test échoue sinon.

12. Observabilité opérationnelle

Les journaux sont ceux de Docker : docker logs takienta-site. Le contrôle de santé est GET /health (nginx répond 200 ok sans journal d'accès). Il n'y a ni alerte, ni métrique, ni analytics. site/config.mjs annonce une rotation des journaux à 30 Mo cumulés (json-file, 10 Mo, 3 fichiers) ; le compose ne configure pas la journalisation, et le réglage qui s'applique n'est pas établi Non déterminé à date.

13. Sécurité opérationnelle

  • Aucun secret dans le dépôt ; le dossier local-secrets/ est ignoré par Git. Ne jamais copier la valeur d'un jeton dans un fichier suivi, une note ou un message.
  • Les jetons npm et PyPI sont personnels et restent sur le poste de travail. Un jeton utilisé une fois dans un outil doit être révoqué ou limité au projet.
  • En-têtes HTTP : voir l'architecture (§4.3). HSTS n'est pas envoyé et la version de nginx est visible.
  • Aucun audit de dépendances n'est défini (ni commande, ni job).
  • Le site n'envoie aucun script ; toute évolution qui introduirait une collecte, un cookie ou un prestataire entraîne la mise à jour de la page de confidentialité et de sa date.

16. Mise à niveau

Les versions sont épinglées par pnpm-lock.yaml (--frozen-lockfile en CI et dans le Dockerfile) ; TypeScript reste en 5.x. Les deux versions de paquet (packages/js/package.json, packages/python/pyproject.toml) et __version__ dans __init__.py doivent rester identiques : tests/test_croise.py les compare. La pratique de mise à jour des dépendances (au cas par cas ou selon une procédure) n'est pas écrite Non déterminé à date.
